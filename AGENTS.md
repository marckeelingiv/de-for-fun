# AGENTS.md

Compact guidance for AI agents working in this repo.

## Toolchain

- **Python 3.13, managed by `uv`.** Always invoke Python/dbt via `uv run` (e.g. `uv run python src/...`, `uv run dbt ...`). Never activate `.venv` manually or use bare `python`/`dbt`.
- No lock on lint/typecheck/formatter tooling — none is installed or configured. Do not invent `ruff`/`mypy`/`pytest` commands; they are not part of this project's verification flow.
- The only test suite is `make test-mcp` (`src/test_mcp_server.py`, `unittest`). It auto-skips if `dbt_project/target/semantic_manifest.json` or `dev.duckdb` are missing, so run `make dbt-compile` (or `dbt-parse`) first to generate the manifest.

## Infrastructure prerequisites

- The whole stack runs on a local **k3d** (k3s in Docker) cluster. Docker must be running on the host before `make up`.
- Bootstrap order is strictly: `make setup` (one-time, installs k3d+kubectl) → `make up` (create cluster) → `make deploy` (apply manifests + bootstrap MinIO + create Redpanda topics).
- `scripts/create_cluster.sh` maps the repo to `/workspace/de-for-fun` inside the k3d container; the Dagster deployment's `hostPath` depends on this mapping. Don't change one without the other.
- Cluster context is `k3d-sandbox`. Services are reached via port-forwards/LoadBalancer ports: MinIO 9000/9001, Dagster 3000, Lightdash 8080, Redpanda 9092, Redpanda Console 8083.

## Pipeline order

Data flows: **generate → buffer → mount → dbt-run → (mcp/orchestrate)**. Each step depends on the previous producing artifacts.

1. `make generate [ROWS=N]` — Polars generator streams JSON to Redpanda topics.
2. `make buffer` — `buffer_writer.py` consumes Redpanda, writes partitioned Parquet to MinIO. Runs until idle/killed; run in a separate terminal from `generate`.
3. `make mount` — registers DuckDB views over MinIO Parquet via `httpfs`.
4. `make dbt-run` — builds staging views + mart tables in DuckDB. Requires MinIO data.
5. `make dbt-test` — exists but test coverage is thin (see TODO.md).

Skipping ahead (e.g. `dbt-run` before `buffer`) fails with empty/missing Parquet.

## dbt & DuckDB gotchas

- **dbt profiles live in `dbt_project/profiles.yml`, not `~/.dbt/`.** Every dbt command must pass `--project-dir dbt_project --profiles-dir dbt_project`. The Makefile does this; if invoking dbt by hand, replicate it.
- **`DUCKDB_PATH` must be an absolute path** when set via env. The Makefile sets `DUCKDB_PATH=$(CURDIR)/dbt_project/target/dev.duckdb` for dbt/mount/query/verify targets. The dbt profile's internal default (`target/dev.duckdb`) resolves relative to `--project-dir`, not CWD — don't "fix" it to an absolute path.
- The shared DuckDB file is `dbt_project/target/dev.duckdb`. The old `data/compute.duckdb` path is deprecated; `data/` is no longer used for DuckDB storage.
- `dbt_project/target/` is gitignored and regenerated by dbt; `manifest.json`, `semantic_manifest.json`, and `partial_parse.msgpack` live there.
- **`dbt-metricflow` is NOT installed** (see KNOWN_ISSUES #8/#16). The MCP server queries DuckDB directly from `semantic_manifest.json` instead of using `dbt sl query`. Don't add `dbt sl` commands without first adding the dependency.

## MCP server (`src/mcp_server.py`)

- Uses `fastmcp`. Two transports: `make mcp` (stdio, for LLM clients) and `make mcp-http` (HTTP on :8079).
- **Primary path (DuckDB direct) needs no infrastructure** — only `semantic_manifest.json` + `dev.duckdb`. Lightdash API tools are optional and no-op when `LIGHTDASH_URL`/`LIGHTDASH_TOKEN` are unset.
- **Manifest is loaded at import time** (KNOWN_ISSUES #15). After changing dbt models/metrics, re-run `make dbt-compile` and restart the MCP server to pick up new definitions.
- Charts are written to `charts/` (gitignored, top-level) — not `dbt_project/target/charts/`.

## Dagster orchestration

- `make orchestrate` starts Dagster dev UI on :3000 loading `src/orchestration/definitions.py`.
- Assets (`src/orchestration/assets.py`) shell out to `src/generator.py`, `buffer_writer.py`, `verify_data.py` via `subprocess.run` with `cwd=PROJECT_ROOT`, then run dbt via `dagster-dbt` using the manifest at `dbt_project/target/manifest.json`.
- All dbt model assets are wired to depend on `minio_data_verified` via `ProjectSandboxDbtTranslator`.
- `buffer_writer` asset intentionally allows `TimeoutExpired` (long-running consumer) — not a failure.

## Data model quick reference

- Two domains: `arena` (SEG) and `podium` (Podium). Four source tables: `fan_pings`, `pos_transactions`, `interaction_events`, `ai_telemetry`.
- Redpanda topics: `seg.fan-pings`, `seg.pos-transactions`, `podium.interaction-events`, `podium.ai-telemetry`.
- MinIO bucket: `data-lakehouse`. Partition path: `{domain}/{table}/tenant_id={tenant}/year=YYYY/month=MM/{batch_id}.parquet`. All four source schemas include `tenant_id` as the first hive partition column.
- dbt layout: `models/base` (tables from Parquet) → `models/staging` (views) → `models/marts` (tables, includes semantic models + metrics + time spine). 13 models, 4 semantic models, 8 metrics.

## When editing source

- Shared config (endpoints, schemas, topics, partition paths, env-driven dataclasses) lives in `src/config.py` — change schemas there, not just in generators.
- Generators are split: `generator_seg.py` (arena), `generator_podium.py` (podium), `generator.py` (combined orchestrator). Keep schemas in sync with `src/config.py` and dbt base models.
- `KNOWN_ISSUES.md` tracks resolved and open issues with file references — check it before "fixing" something that may already be resolved or intentionally deferred.
- `TODO.md` lists planned future work (CI, dbt tests, Great Expectations, manifest reload tool).
